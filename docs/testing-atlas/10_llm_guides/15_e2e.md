# E2E: End-to-end controlled-boundary testing

## Family law

For mfact, end-to-end means the chain mfact controls: TTL → ggen → Lean → Lake → auditor. External runtime/cloud correctness is consumer-owned.

## Mandatory implementation sequence

1. Start from canonical TTL, never handwritten Lean.
2. Run/represent the ggen projection.
3. Require the projected Lean declaration to compile and be kernel checked.
4. Require the intended Lake target/test driver.
5. Derive the audit from the compiled environment and manifest.
6. Compare the terminal standing to the expected crown claim.

## Core-team anti-patterns

- Starting the e2e test inside Lean.
- Adding FFI/runtime verification to mfact's scope.
- Trusting generated file names without provenance.

## Lean/Lake skeleton

```lean
TTL fixture
  → ggen expected projection
  → `lake build <target>`
  → environment-derived theorem/axiom inventory
  → manifest reconciliation
  → standing receipt
```
