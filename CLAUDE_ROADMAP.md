# CLAUDE ROADMAP — MULTIFRACTAL WORKFLOW / CHATMAN ECOSYSTEM

## Mission

Finish the Multifractal Workflow runtime as a standing-preserving autonomic process system.

Do not treat this as a workflow-engine feature project.

The category change is:

**An executing process autonomically increases its own process resolution until the parent goal becomes lawfully executable.**

The crown loop is:

admitted graph state
→ semantic closure and contraction
→ unresolved required state
→ PDDL plan to make that state true
→ POWL manufacture of the required process layer
→ local BCINR execution or external Arazzo projection
→ brokered hook/dispatch actuation
→ returned consequence as raw observation
→ re-admission
→ SPARQL CONSTRUCT graph consequence
→ parent closure or another autonomically manufactured layer

Continue until the enterprise goal reaches declared terminal standing.

The target is not AI that recommends what to do.

The target is a process machine that manufactures missing work, executes machine-actuable transitions by default, dispatches external work lawfully, admits consequences, and grows more process only where semantic closure cannot already finish the job.

# 1. Non-negotiable doctrine

## Standing

A = μ(O*)

R = receipt(A)

Raw observation O has no standing. Only admitted observation O* enters manufacture μ.

Generation creates candidates. Admission creates standing. Receipts bind consequence, provenance, conformance, and replay. Replay proves receipts are not ornamental.

Never silently promote UNKNOWN to ADMITTED, UNSUPPORTED to REFUSED, or STATED/EXTRACTED to PROVEN.

## Zero unreceipted actuation

The broker is the only DO path.

No dialect, LLM, CLI, script, direct integration, Erlang process, WASM module, or generated runtime may bypass it.

Before actuation verify standing, role, authority, conformance, hook contract, input lineage, idempotency, correlation, and required prior receipts.

After actuation capture the actual consequence, bind it to dispatch, emit evidence, update state only through admitted consequence, extend the receipt chain, and preserve replay identity.

## Refusal is not implementation

A typed refusal is correct only when the capability is genuinely outside the admitted support surface or input is invalid.

Do not use refusal as a placeholder for a missing implementation.

This repository already demonstrated the failure mode: a parser accepts a construct, lowering skips or refuses it, tests prove the refusal, and the ticket claims the gap is mechanically handled. Production capability is still absent.

When the specification construct is in scope and mechanically implementable, implement it.

## Tera renders syntax, never semantics

PDDL
→ POWL
→ SPARQL render model
→ Tera
→ Arazzo

Tera must not decide topology, order, branching, recursion, retries, compensation, or authority. Those decisions already exist in admitted graph state and POWL geometry.

## Public semantics over private semantic authority

Prefer RDF/RDFS, PROV-O, DCTERMS, DCAT, SKOS, SHACL, ShEx, ODRL, OCEL, OpenTelemetry semantic concepts, OpenAPI, Arazzo, PDDL, and POWL.

Private extensions may carry transport metadata or local identity. They must not become hidden semantic authority.

## N3 remains quarantined

N3 is a bounded implication/refinement escape hatch, not the default dialect.

Require explicit profile capability, bounded cost, builtin whitelist, controlled execution, receipts/replay, and no direct actuation.

Prefer SHACL/ShEx, SPARQL, SPARQL CONSTRUCT, Datalog, and bounded closure before N3.

# 2. The actual Multifractal Workflow theory

## The key insight

Multifractal Workflow is not primarily a post-hoc statistical statement about scaling.

The primary mechanism is:

**The graph autonomically adds process layers until the work is finishable.**

At a workflow activity ask:

What must be true for the parent process to continue?

The graph establishes what is currently true.

Datalog and bounded N3 derive what is already logically true.

SHACL/ShEx refuse inadmissible states.

If the required state is still false but reachable, PDDL finds a transition path.

POWL manufactures that path as a child process layer.

That child may expose another unresolved required state.

Repeat:

W0[a ↦ W1]
W1[b ↦ W2]
W2[c ↦ W3]

until leaves resolve to executable hooks or declared external dispatch.

The process grows to the resolution required by reality.

## Why PDDL is indispensable

RDF tells us what is true.

Datalog derives closure.

N3 performs bounded contextual implication/refinement.

SHACL/ShEx admit or refuse structure.

None of them answers:

Given state S, available actions A, and required state G, which lawful action sequence makes G true?

That is the planning problem.

PDDL connects semantic contraction to actuation.

Current admitted state
+ hook-achievable effects
+ goal predicate
→ lawful transition path

Without PDDL, the system can know why it is blocked but cannot generally manufacture a route to make the missing state true.

Without POWL, the path does not become composable process geometry.

**PDDL discovers necessary work. POWL turns necessary work into process.**

## Resolution-minimal growth

For required goal predicate g:

1. Compute semantic closure.
2. Apply bounded refinement.
3. Validate admissibility.
4. Ask whether g is already true.
5. If impossible/inadmissible, refuse.
6. Only if g remains false and reachable, invoke PDDL.
7. Manufacture the plan as POWL.

The crown rule:

**Datalog and N3 subtract inference from work; PDDL identifies the irreducible state-transition residue; POWL manufactures only that residue as process.**

## Why multifractal

The same growth law recurs at every scale:

observe
→ admit
→ close semantics
→ identify unresolved state
→ plan
→ manufacture process
→ actuate/dispatch
→ observe consequence
→ re-admit

But local geometry differs because reachable state spaces differ.

Software can produce wide parallel decomposition.

Legal can produce narrow deep authority chains.

Logistics can produce massive fan-out.

Human approval can produce shallow structure with high waiting mass.

Cross-engine execution can produce long-lived supervised branches.

The same execution law recursively manufactures heterogeneous local geometry.

That is Multifractal Workflow.

# 3. Yin/Yang runtime boundary

## Yin: RDF dialects contract the problem

Raw scenario space
→ ontology typing

→ bounded N3 refinement
→ SHACL/ShEx admission
→ smallest unresolved lawful state

The graph side answers:

- what kind of thing is this?
- what follows from what is already known?
- which states are impossible?
- which contextual refinement applies?
- what is already true?
- what genuinely remains unresolved?

A derivable relation must not become a PDDL action.

Logical consequence is not labor.

## Yang: hooks expand what can be done

The hook registry increases the executable action surface.

A PDDL action should correspond to an effect the ecosystem can actually realize through a hook or external dispatch contract.

Execution classes:

- LOCAL_ACTUATION
- EXTERNAL_MACHINE_DISPATCH
- EXTERNAL_HUMAN_DISPATCH

Machine actuation is the default. A human is one execution class, not the universal runtime.

**RDF dialects make the world small enough to plan; hooks make the planner's conclusions real without routing every transition through a person.**

## PDDL is the bridge

Available hooks change the planning universe.

A new hook introduces a new achievable effect.

PDDL gets a shorter or different path.

POWL geometry changes automatically.

This also creates the capability roadmap signal:

Semantic pressure: the graph repeatedly cannot close a relation cheaply.

Actuation pressure: PDDL repeatedly terminates in human work because no machine hook realizes the required effect.

The runtime can identify where the semantic surface is too wide and where the actuation surface is too narrow.

A conventional LLM may reason:

In a normal agent architecture that remains prose.

After admission, the relation is available to SELECT, Datalog, SHACL, PDDL projection, POWL manufacture, hooks, OCEL analysis, and future workflows.

**CONSTRUCT capitalizes semantic work.**

# 10. Lessons from the v26.7.11 audit

Treat the repository as fast-moving and concurrently modified.

Do not trust a ticket status, docstring, assistant summary, or passing local unit test without checking current reachability.

## Area-scoped audits missed cross-cutting failures

Permanent rule:

Audit invariants across the call graph, not only crates or ticket areas.

Use cross-cutting lenses:

- correctness/determinism
- security/safety
- test rigor
- integration/reachability
- claims honesty

## Production reachability is a standing surface

A public function may be real, tested, and correct but have zero production callers.

Trace every claimed mechanism:

real entrypoint
→ call graph
→ mechanism
→ consequence
→ next state

No dead-end library islands.

Formally: `REAL_EDGE(A, B) ⟺ ∃ f_prod : B(A(x))` — a production caller actually applies B to
A's output. `TEST_ONLY_EDGE(A, B) ⟺ ∃ f_test : B(A(x)) ∧ ¬∃ f_prod` — only a test connects
them. `REAL(A) ∧ REAL(B) ∧ MISSING_EDGE(A, B) ⇒ CausalHole` — two real, correct, tested
mechanisms with no edge between them is the exact shape of a dead-end library island; a
`TEST_ONLY_EDGE` is the same defect with the edge merely disguised as reachable. An audit
claiming "production reachability proven" must exhibit the `f_prod` witness, not a passing
test suite.

The Arazzo runner audit already found a return-admission path that was heavily tested while the real dispatch path captured I/O results without feeding them back into AIR state — a `TEST_ONLY_EDGE` from dispatch result to AIR state, silently reported as `REAL_EDGE`.

## No check-then-act races

Dispatch deduplication must use atomic insert/CAS semantics.

Duplicate delivery must not actuate twice, overwrite winner state, or poison consequence admission.

## Public IDs are not authority tokens

Do not derive actuation/return authority from unsalted hashes of public workflow and step IDs.

Use real server-side secret/nonce-backed authority material.

## OTel→OCEL cannot be a self-verifying island

A real projection library is insufficient if production never calls it.

The external observation path must reach:

telemetry observation
→ RDF admission
→ CONSTRUCT
→ OCEL
→ receipt
→ next MFW state

Validate runtime graph IRIs. No panic on external values.

Independent receipt oracles must not copy the SUT algorithm byte-for-byte.

## Timing benchmarks are not correctness tests

Separate correctness, performance comparison, and benchmark suites.

A noisy timing test must not fail-fast before correctness tests execute.

## Rigor-linter lesson

`scripts/rigor_linter.py` (verified live 2026-07-13, Pass 30) implements 13 distinct
tripwires. Enumerated in full here so this section can't silently undercount again:

- fake Lean 4 syntax (`def hello := "world"`) [rigor_linter.py:16-17]
- unproved theorem / `sorry` in `.lean` files [rigor_linter.py:25-26]
- empty trait definitions (`pub trait X {}`) [rigor_linter.py:31-32]
- zero-field marker structs (`pub struct X;`) [rigor_linter.py:35-36]
- PhantomData-only structs [rigor_linter.py:44-51]
- empty trait implementations (`impl X for Y {}`) [rigor_linter.py:58-64]
- `unimplemented!()` / `todo!()` [rigor_linter.py:67-68]
- dead alternative functions (`_v2`, `_alt`, `_correct`, `_fixed`, `_working`)
  [rigor_linter.py:71-72]
- discarded-input + unconditional `Ok(())` [rigor_linter.py:75-76]
- discarded-input + any unconditional constructor, broader form
  [rigor_linter.py:83-88]
- forbidden sci-fi vocabulary (Warp Drive, Bekenstein bound, Heat Death,
  SubKolmogorov, Quantum Blocker) [rigor_linter.py:91-94]
- claim-without-mechanism doc comments -- enforcement language above a body with

implemented (self-audit Pass 1 finding PA29 caught an earlier version of this list

the 13 real checks -- same overclaim pattern in both directions: don't round this list
to whatever's quick to type in either direction, enumerate it against the live file.

The linter is not semantic proof. It makes suspicious mechanism gaps cheap to find.

## Diagrams are audit instruments

Maintain C4 context/container/component coverage and sequence diagrams for every production entrypoint, consequence return, refusal, restart/replay, compensation, cross-engine dispatch, OTel→OCEL, PDDL→POWL substitution, Arazzo→AIR, and OTP/AtomVM differential flow.
